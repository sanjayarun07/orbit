## Problem and current baseline

A live four-turn VVV/DIEM research comparison is documented in `reports/dual-token-eval/report.md`; its prompts are in `evals/journeys/dual-token-2026-09-24.json`. The current path retains the research objective and uses a stronger research model, but the fourth turn—“which other projects follow lock collateral → mint a tradable second token”—still has weak recall and admits loose analogues. A second pattern-specific search improved recall while admitting false matches. Do not solve this by adding another prompt-specific regex, hard-coded project list, or unconditional search.

The existing foundations are `app/contracts.py` (question contract and model planner), `app/tool_catalog.py` (coverage and eligibility), `app/evidence_pipeline.py` (retrieval and synthesis), `app/facts.py` and `app/fact_gate.py` (fact normalization and verification), `app/research_objective.py` (multi-turn objective), `app/perplexity_tools.py` (web sources), `app/url_reader.py` (reading a URL supplied by the user), and `scripts/episode_eval.py` plus `evals/episodes/` (end-state evaluation). The contract pipeline and discovery-first research flags are currently enabled by default in `app/settings.py`. Inspect the actual call path before changing it, including legacy routing and streaming behavior. In the current contract pipeline, the structured Perplexity search returns a cited answer and source list, but its cited search hits are not automatically opened and checked before synthesis. The existing URL reader is primarily a separate path for a URL the user supplied; reuse its safe fetch behavior where appropriate rather than assuming it already verifies search hits.

## Target behavior

One question contract should drive a bounded cycle:

1. Interpret the current user turn together with relevant conversation context. Record the subject and identity, the exact question, requested scope/venue/window/filters, required evidence, and any ambiguity. Context may resolve “it”; it must not turn the previous topic into the current question or silently drop user constraints.
2. Shortlist **capabilities** (for example web discovery, source-page reading, token identity, on-chain ownership, market state, wallet state, execution quote) from a catalog derived from existing tool metadata. The model can reason about what evidence it needs. Deterministic eligibility must still reject tools whose identity, scope, metric, coverage, freshness, or required inputs cannot satisfy the contract. Do not duplicate the catalog in a second hand-maintained table if the current catalog can be extended.
3. Separate **discovery** from **inspection**. Search results and provider-written summaries propose URLs and candidate answers; fetch the most relevant cited pages and extract the passages needed to test material claims. Preserve URL, page title, publisher, publication/as-of date when available, retrieval time, and the passage or locator. A URL that cannot be read may be cited as a search-result lead, but must not be represented as verified page evidence. When direct extraction fails, use one bounded alternative reader or search-index view and label its weaker provenance.
4. Fetch the smallest useful evidence set. After each retrieval round, compare the *facts obtained* with the contract. If a named gap has a capable source, make a targeted follow-up call; otherwise stop and state the gap. Put explicit limits on model calls, provider calls, time, and money. Independent eligible calls may run concurrently. Record why every selected or rejected source was considered.
5. Synthesize only from accepted evidence. Verify material claims after synthesis, including named entities, dates, figures, and **relationships/mechanisms**. A source mentioning a project is insufficient to prove that the project uses the requested mechanism. Where verification fails, repair once if evidence is available; otherwise withhold or qualify the claim. Preserve numbered source links and as-of dates in the UI answer.
6. Return an honest answer or an explicit, useful abstention. A global ecosystem ranking is not a venue-trade ranking; a token-price card is not a mechanism explanation; a search snippet is a candidate, not proof from the underlying page. No answer should claim a source scope, freshness, or entity relationship the evidence does not support.

Keep exact-state requests state-first: connected wallet balances, holders, quotes, exit analysis, positions, swaps, and other account or chain facts must use appropriate state providers and existing authorization gates. Discovery-first remains appropriate for open-ended research, but web prose must not silently substitute for those state facts. Do not widen execution privileges or weaken approval/consent behavior.

## First implementation slice

Make the end-to-end loop work for `open_research` first, using the four-turn VVV/DIEM journey as the primary case. The last turn must search for the *specific* mechanism and test each candidate against its primary-source description. It should distinguish an exact match from adjacent designs such as receipt tokens, wrapped assets, ordinary stablecoin CDPs, burn-for-nontransferable-credits, and collateral provided by a different asset. If no additional project is verified, say so; do not invent one to satisfy the prompt. A relevant project may only be presented as a match when the source supports all material conditions. Do not hard-code AI Surplus, Venice, Akash, or any other project as an expected answer.

Remove or subsume the narrow pattern-specific second-search branch in `app/evidence_pipeline.py` once a general gap-driven retrieval loop replaces it. Remove superseded routing paths rather than accumulating yet another interception layer. Keep the existing contract path and user-visible streaming semantics compatible. If the new loop needs a flag, use one clear rollout flag and define the old-path fallback; do not create multiple overlapping modes.

Before expanding to other contract kinds, demonstrate that the new `open_research` loop improves the actual answer without regressing ordinary research questions. Then extend the same decision mechanism to market rankings, holders, recent events, and yields only where it removes existing special cases and passes their episode goals. Avoid a wholesale rewrite of account, execution, or UI code.

## Evaluation and acceptance

Add recorded, source-linked episodes that exercise the full research path, not only the planner or tool ranker. Include the four-turn journey, each turn in context; paraphrases and reordered constraints; ambiguous entity names; a search result whose snippet asserts a mechanism but whose page does not; a source that mentions but does not prove a mechanism; a qualifying source discovered only by a second retrieval axis; an unreadable source page; missing/stale sources; and a provider failure. Use fixtures for deterministic replay and keep live probes separate. Score the end state: resolved identity, constraints retained, discovery queries and extracted URLs, unsupported sources rejected, verified matches and near-misses labelled correctly, citations, abstention, provider calls, and latency. A lexical judge alone is insufficient for the mechanism claim; use a structured human-reviewed fixture or a reproducible relationship check, and report any model-judge limitations.

Run repeated trials at `k=5` for baseline and candidate on the same recorded cases, with caching controlled so repetition is meaningful. Report pass^5, wrong-answer rate, unsupported-claim rate, median and p95 latency, model calls, provider calls, and estimated cost. Run the focused tests and `pytest -q`. Run a small live comparison if credentials and the app are available; do not make passing live providers a requirement for deterministic CI. Capture transcripts and artifacts under a dated `reports/` directory. Do not claim improvement from a single successful run or from tool-selection accuracy alone.

Acceptance is a reviewable diff plus evidence that the new path improves or matches baseline on research answer correctness, does not increase unsupported mechanism claims, and preserves existing security and exact-state behavior. If results are inconclusive, leave rollout disabled and report what failed. In your final response, identify changed files, explain the routing/evidence decision flow, provide the comparison table and test results, and state remaining risks. Do not commit or push unless explicitly asked.
